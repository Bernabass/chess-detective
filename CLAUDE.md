# Retrograde

Chess detective puzzles built on **retrograde analysis**: players reason *backwards* from a position to work out how it arose.

- Full product + technical spec: `docs/SPEC.md`. Read the section for the current phase before starting work.
- Progress log: `docs/PROGRESS.md`. Decision log: `docs/DECISIONS.md`. Learning notes: `docs/learning/`.

## What we're building (v1)
- **Lab**: set up or paste any position. The engine explains in plain English whether it is legal, lists possible last moves, and can "prove" legality by finding a game that reaches it.
- **Daily Proof Game**: a Wordle-style daily puzzle. Reach the target position from the starting position in exactly N plies. Six guesses, per-ply colored feedback, hints, streaks, leaderboards.
- **Accounts**: username/password and "Sign in with Lichess"; guest play; daily and all-time leaderboards.

## Repo map
- `packages/engine/`: TypeScript chess + retro engine. Pure, deterministic, zero runtime deps. The heart of the project.
- `apps/web/`: React + Vite + TypeScript frontend. Board UI is chessground. The engine runs in a Web Worker.
- `apps/generator/`: Node CLI that generates and verifies daily puzzles (JSONL output).
- `services/api/`: Go HTTP API + PostgreSQL. In production it also serves the built web app (embed.FS).
- `api/openapi.yaml`: the API contract and source of truth for both Go and TypeScript.
- `fixtures/`: cross-language test vectors generated by the TS engine and checked by the Go tests.
- `scripts/`: cross-platform Node helper scripts used by the root `package.json` scripts.
- `docs/`: spec, progress, decisions, learning notes.
- Path-scoped rules for each area live in `.claude/rules/` and load when you touch those files.

## Commands (root `package.json` scripts; set up in Phase 0, keep this list accurate)
- `pnpm install`: install JS deps; its `prepare` script also points git at `.githooks/`
- Database: the owner's **local PostgreSQL**, configured by `DATABASE_URL` in `.env`. `pnpm db:up` / `pnpm db:down` (Docker) exist only as an optional alternative.
- `pnpm dev`: run the Go API and the Vite dev server together (Vite proxies `/api` to Go). The API refuses to start while migrations are pending: run `pnpm db:migrate`
- `pnpm check`: lint + typecheck + fast tests for every TS package, plus `go vet`, golangci-lint and Go unit tests. Must pass before every commit.
- `pnpm --filter @retrograde/engine test` / `test:slow`: engine fast / slow suites (same for `@retrograde/generator`; both slow suites run nightly in CI)
- `pnpm test:api`: Go unit + integration tests (needs Postgres running)
- `pnpm test:e2e`: Playwright end-to-end tests against the production web build, a real API on fixture puzzles and a fake Lichess (needs PostgreSQL and `TEST_DATABASE_URL`, like `pnpm test:api`; first install the browser once: `pnpm --filter @retrograde/web exec playwright install chromium`); `pnpm --filter @retrograde/web shots` takes the review screenshots into `apps/web/screenshots/`
- `pnpm gen`: regenerate sqlc code, Go server stubs and TS API types from `api/openapi.yaml`
- `pnpm db:migrate`: apply database migrations; `pnpm seed`: migrate, set `LAUNCH_DATE` in `.env` if missing, load `data/puzzles-v1.jsonl` and schedule dailies through 30 days ahead (idempotent)
- `pnpm try:api`: build and start a private API on port 8091 and walk through the daily flow (guest, wrong guess, hint, solve, register, leaderboards), printing each response. Needs `pnpm seed` first
- `pnpm --filter @retrograde/generator start -- generate --count 30 --seed 7 --max-plies 8 --width 40 --jobs 4 --out puzzles.jsonl`: generate a small pool in under a minute (`verify` / `stats <file>` check and summarize a file; paths are relative to where you run it). The beam's cost depends on `--width` and `--max-plies`, not `--count`: the full committed pool (`--count 500 --seed 1 --jobs 4`, defaults otherwise) takes about 72 minutes.

## Development environment (IMPORTANT)
- The owner develops on **Windows 10 in VS Code** with the Claude Code extension. Everything must work there first, and also on Linux (CI).
- The project folder is the current VS Code workspace folder. Its path may contain spaces: always quote paths in commands and scripts. Never move the project elsewhere.
- PostgreSQL tools may not be on `PATH`; look in `C:\Program Files\PostgreSQL\<version>\bin`.
- No `make`. All tasks are root `package.json` scripts that work in cmd.exe, PowerShell and bash: no `cd a && b` (use `go -C services/api …`), no `rm -rf` (use `rimraf`), no `VAR=value cmd` (use `.env` or Node scripts in `scripts/`), and `concurrently` for parallel processes.
- Go programs load `.env` themselves in development. Never require the user to export env vars by hand.
- Your shell on Windows may be Git Bash or PowerShell. Use forward-slash paths in code and config, and never assume Linux-only tools exist.
- Line endings are LF everywhere (`.gitattributes`). Don't create CRLF files except `.bat`/`.cmd`/`.ps1`.

## Git and authorship (IMPORTANT)
- Every commit must be authored and committed by the identity in the repo's `git config user.name` / `user.email`. That is the owner (their name and email, set once during setup). Never change `user.*` config afterwards, never pass `--author`, and never add co-author lines.
- Commit messages and PR descriptions contain no AI attribution: no `Co-Authored-By` trailers for Claude, no "Generated with Claude Code", no session links. `.claude/settings.json` disables them and `.githooks/commit-msg` strips them as a backstop. Don't disable or bypass hooks (no `--no-verify`).
- Small commits, Conventional Commits style, e.g. `feat(engine): add unmove generator`.
- Never force-push, rewrite pushed history, or delete tags.

## Engineering rules
- TypeScript: `strict` mode, no `any` (use `unknown` and narrow), ESM only, named exports.
- Engine: no DOM, no Node APIs, no runtime dependencies. Randomness only through an explicit seeded RNG passed in. Hot paths avoid allocation (typed arrays, numeric move encoding).
- Go: standard library first; wrap errors with `%w`; `log/slog` for logging; pass `context.Context` into every DB call; no global mutable state.
- SQL lives in `services/api/db/queries/*.sql` (sqlc). Migrations are append-only (goose).
- Secrets come only from environment variables or the gitignored `.env`. Keep `.env.example` current; never commit passwords, tokens or `.env`.
- The daily puzzle **solution never leaves the server** until the player has solved it or used all guesses.
- Accessibility: never convey feedback by color alone; pair colors with icons or labels.

## Gotchas
- Internally everything counts **plies**. "Proof game in 4.0" = 8 plies; "4.5" = 9 plies.
- Daily targets compare **piece placement + side to move** only (not castling rights, en passant or clocks).
- The Go API validates guesses with a Go chess library, so chess rules exist in two languages. `fixtures/replay-vectors.json` keeps them in agreement; regenerate it whenever engine move rules change.
- A synchronous search in a Web Worker can't receive a cancel message. Cancel by terminating the worker.
- Chessground is GPL-3.0, so this repository is GPL-3.0-or-later. Don't add dependencies with incompatible licenses.
- When compacting, preserve: the current phase, failing tests, files modified in this phase, open TODOs.
