# Phase 6: API core

Phase 6 is the server: a Go HTTP API over PostgreSQL that runs the Daily Proof Game. It serves the puzzle, judges guesses, gives hints, keeps stats and streaks, handles accounts and sessions, and ranks players. There's no UI for it yet (that's Phase 7), so `pnpm try:api` walks through it from the terminal.

Code: [services/api/](../../services/api/). The rules live in [internal/daily/](../../services/api/internal/daily/), [internal/auth/](../../services/api/internal/auth/) and [internal/leaderboard/](../../services/api/internal/leaderboard/). HTTP is in [internal/httpapi/](../../services/api/internal/httpapi/), SQL in [db/queries/](../../services/api/db/queries/), and the schema in [db/migrations/00002_schema.sql](../../services/api/db/migrations/00002_schema.sql).

## 1. Risk first: chess rules in two languages

The browser plays moves with our TypeScript engine, but the server must judge guesses itself (never trust the client). So the chess rules exist twice, and the two must agree.

- [internal/chessrules](../../services/api/internal/chessrules/replay.go) wraps the Go library `corentings/chess` (MIT). It works on *positions*, not the library's `Game` object, because `Game` ends a game on fivefold repetition, and our engine doesn't.
- **Test vectors keep the two languages honest.** [fixtures/replay-vectors.json](../../fixtures/replay-vectors.json) is generated by the TS engine: 520 legal games (with the final position and the SAN of every move) and 132 illegal ones (with the ply that breaks). The Go test replays them all. This was the first thing built, before any API code depended on it, and the library agreed with the engine on every vector.
- The feedback rules (§8.3) get the same treatment: [fixtures/feedback-vectors.json](../../fixtures/feedback-vectors.json) comes from a TS reference implementation, and Go must produce the same G/Y/X strings.

## 2. Contract first

[api/openapi.yaml](../../api/openapi.yaml) is the source of truth. `pnpm gen` turns it into:

- a Go *strict server* interface: each handler gets a typed request and returns a typed response;
- TypeScript types for the web app.

So the two sides can't drift. Every request is also **validated against the contract** by middleware (kin-openapi): unknown JSON fields, lengths, patterns and enums are rejected with a 400 before a handler runs. SQL works the same way: queries are written in `.sql` files, and **sqlc** generates typed Go functions from them, so there's no SQL string-building in Go (no SQL injection by construction).

## 3. The guess, in one transaction

[daily/service.go](../../services/api/internal/daily/service.go) `Guess` follows SPEC §10.5:

1. Find the puzzle (a future one is a 404: it doesn't exist yet as far as players know).
2. `SELECT … FOR UPDATE` the player's attempt row. This is the key to **concurrency**: if the same player sends two guesses at once (a double click, two tabs), the second transaction waits for the first to finish. So "six guesses at most" can't be beaten by a race. `TestConcurrentSixthGuess` fires two sixth guesses at once and checks for exactly one 200, one 409, and six stored guesses.
3. Reject a finished attempt or a seventh guess (409), a wrong length or an illegal move (422, with the 1-based ply).
4. Replay the guess with `chessrules`, compute the feedback, and store it.
5. Solved means the guess reaches the target's **piece placement and side to move**, so a different move order that reaches the same position also wins.
6. On solve or the sixth miss, finish the attempt and recompute the stats, still inside the same transaction.

**The solution never leaves the server before the attempt is finished.** The domain type only fills `Solution` for finished attempts, and `TestNoSolutionLeak` scans every response a player can get (GETs, start, five wrong guesses, all three hints, archive, leaderboard) for any solution move. The one exception is hint 3, which reveals exactly one move.

## 4. Stats and streaks without drift

There are two ways stats can change: finishing an attempt, and a guest's attempts merging into an account. Instead of two "update the counters" code paths, there's one: `RecomputeStats` rebuilds a player's stats from their finished daily attempts with the pure function `ComputeStats` ([stats.go](../../services/api/internal/daily/stats.go)). It's unit-tested without a database.

- A solve counts for the **puzzle's day**, not the clock's: start #3 at 23:59 and finish at 00:01, and it's still #3's day. Whether an attempt is archive practice is decided once, when it starts.
- The stored "current streak" is as of the last solve. Whether it's still alive depends on *today*, so that's applied when reading: a streak counts only if the last solve was today or yesterday. A failed daily ends it at once.
- Domain code never calls `time.Now()`. A `Clock` interface is injected, and tests use a fake clock to cross midnight, expire sessions, and refill rate limits.

## 5. Sessions and accounts

- **Passwords:** argon2id (m = 19 MiB, t = 2, p = 1), stored as a self-describing PHC string. Logging in as an unknown user still runs one hash check, so response time doesn't reveal which usernames exist.
- **Session tokens:** 32 random bytes in an HttpOnly, SameSite=Lax cookie. The database stores only their sha256, so a leaked database backup doesn't contain usable sessions. The expiry slides (30 days after last use), but it's written at most once an hour, so reads don't cause a write per request. Login, register and logout **rotate** the token, which defeats session fixation.
- **Guests:** anyone can play without an account. `GET` requests create nothing; `POST /daily/{n}/start` (which the web app calls when it shows a puzzle) creates the guest and the attempt. When a guest registers or logs in, their attempts move to the account (except puzzles the account already played) and the guest is deleted. A cleanup job deletes expired sessions and guests older than 30 days who never guessed.
- **CSRF:** every state-changing request must be `application/json` with an `Origin` equal to `BASE_URL`. A plain HTML form on another site can't send that, and SameSite=Lax keeps the cookie off cross-site POSTs anyway.
- **Rate limits:** token buckets per IP and per player ([ratelimit](../../services/api/internal/ratelimit/ratelimit.go)). A 429 says when to retry (`Retry-After`).

## 6. Leaderboards in SQL

The daily leaderboard ranks solved, non-archive attempts by guesses, then hints, then time, with a **window function**: `rank() OVER (ORDER BY guesses, hints, seconds)`. Ties share a rank and the next rank skips (1, 2, 2, 4). The caller's own entry is the same query filtered to their player, so they see their rank even outside the top 100. Guests never appear, because the query joins to `users`.

## 7. Testing against a real database

Integration tests (`pnpm test:api`) use the real PostgreSQL, not mocks, because the interesting bugs are in SQL, transactions and locks. [dbtest.Store](../../services/api/internal/dbtest/dbtest.go) gives each test a **fresh schema** (`CREATE SCHEMA t_<random>`, then migrate into it via `search_path`), and drops it afterwards. So tests are isolated and run in parallel. A test also checks with `EXPLAIN` that the hot queries can use their indexes.

## Interview questions you should be able to answer

- *How do you stop a user from submitting a seventh guess by racing two requests?* Lock the attempt row with `SELECT … FOR UPDATE` in the transaction that checks and inserts.
- *Why store a hash of the session token instead of the token?* Whoever reads the database can't impersonate users. It's like storing password hashes, but sha256 is enough because the token is long and random.
- *Why should GET requests have no side effects?* Crawlers, prefetchers and link previews call them freely; here, that would have created a guest row per bot visit.
- *How do you keep two implementations of the same rules in agreement?* Generate test vectors from one and check the other against them in CI.
- *How do you test code that depends on "today"?* Inject a clock.
- *Why recompute stats instead of incrementing counters?* One code path for every way stats can change, so they can't drift apart.
